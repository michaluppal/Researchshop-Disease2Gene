\section{Software Description}
\label{sec:description}

\subsection{System Architecture}

ResearchShop is a cross-platform desktop application and a command-line utility built with Electron~\cite{electron_docs} (TypeScript/React frontend) and Python 3.11+ (extraction pipeline backend). The desktop process and Python pipeline run on the user's machine with no ResearchShop server infrastructure. The workflow uses direct external calls to PubMed through the NCBI Entrez Programming Utilities (E-utilities)~\cite{ncbi_eutilities_help}, PubTator3, PMC, Europe PMC, and Google Gemini as required for paper discovery, open-access retrieval, NER, and LLM extraction. Users provide their own Gemini API key and NCBI Entrez email.

The frontend communicates with the Python pipeline through an inter-process communication (IPC) bridge. The pipeline emits structured JSON messages on standard output (\texttt{PROGRESS:\{...\}}, \texttt{LOG:\{...\}}, \texttt{RESULT:\{...\}}), which the Electron main process parses and forwards to the React renderer. Secrets (API key and email) are passed as environment variables to the spawned Python process, never as command-line arguments.

The pipeline follows the seven implementation domains shown in Figure~\ref{fig:architecture}.

\begin{enumerate}[leftmargin=*,itemsep=1pt]
    \item \textbf{Paper selection} retrieves PubMed records through NCBI Entrez E-utilities~\cite{ncbi_eutilities_help}. Topic results are ranked by gene relevance and capped impact signals from Semantic Scholar citation counts and SCImago Journal Rank~\cite{semantic_scholar_api,scimago_sjr}; user-supplied PubMed identifier (PMID) lists are unchanged.
    \item \textbf{Open-access filtering} admits only papers whose full text can be fetched from PMC or Europe PMC.
    \item \textbf{Paper reading} preserves Journal Article Tag Suite (JATS) sections, tables, captions, image links, and supplementary metadata where available.
    \item \textbf{Candidate discovery} combines PubTator3 NER~\cite{wei2024pubtator3}, deterministic HGNC scanning, and a full-text LLM pass.
    \item \textbf{Detail extraction} fills the user-defined schema and requests source quotations. The default model is \texttt{gemini-2.5-flash-lite}; model identifiers are configurable~\cite{google_gemini_models}.
    \item \textbf{Validation} applies a versioned bundled HGNC snapshot~\cite{braschi2019genenames}, the HGNC Representational State Transfer (REST) service~\cite{hgnc_rest_docs}, MyGene.info~\cite{wu2013biogps}, source grounding, citation checks, and HGVS nomenclature matching.
    \item \textbf{Output writing} uses a bounded worker pool and configurable timeout, then writes primary tables and audit artifacts.
\end{enumerate}

Figure~\ref{fig:architecture} separates proposal, extraction, and validation because these stages have different error profiles. The UI and paper-selection stages decide \emph{which papers} to process; the candidate-discovery stages decide \emph{which gene or protein labels} deserve attention; the LLM stage fills user-defined fields only after receiving source-derived candidates; and the validation layer decides \emph{which rows} are safe enough for the primary export. Hallucinations are constrained at three points: the LLM is seeded with candidates that already came from the source text, every returned gene must be grounded back to the article, and citation-bearing fields must point to recoverable source passages before export.

\subsection{Hybrid NER--LLM Architecture}

The hybrid design separates candidate discovery from contextual extraction. PubTator3 supplies normalized biomedical entities, deterministic HGNC scanning recovers symbols and aliases missed by NER, and an LLM discovery pass proposes additional gene candidates from the full text. A separate LLM detail-extraction pass fills researcher-defined fields for the combined candidate set. Both LLM-proposed candidates and extracted fields remain untrusted until identifier, source-text, citation, and variant checks pass. NER locates entities but does not fill a researcher-defined schema; unconstrained LLM extraction can fill a schema without deterministic evidence constraints.

\subsection{Schema-Driven Extraction}

ResearchShop therefore asks the model to fill user-defined columns rather than a free-form summary, so each run has named fields and a checkable output contract. Users define these columns as natural-language descriptions. For example, researchers might specify:

\begin{itemize}[itemsep=1pt]
    \item \textbf{Key Finding}: Main research finding for this gene
    \item \textbf{Statistical Evidence}: p-values, odds ratios, confidence intervals
    \item \textbf{Functional Impact}: Effect on protein function or pathway
\end{itemize}

The pipeline dynamically constructs LLM prompts incorporating these column definitions, enabling researchers to customise extraction for different contexts (pharmacogenomics, rare diseases, cancer genomics) without code modifications. Every run has named fields, predictable column order, companion citation columns, and validation metadata that can be checked programmatically. For each extracted value, the LLM is required to provide a verbatim citation from the source text. If a requested field is not supported by the paper, the expected behaviour is an empty field rather than a speculative answer.

\subsection{Desktop Application}
\label{subsec:desktop}

The application is packaged with electron-builder. The current public release provides a macOS disk image (\texttt{.dmg}); Windows executable (\texttt{.exe}), Linux AppImage, and Linux Debian package (\texttt{.deb}) targets are supported by the build configuration and remain part of release validation. On first launch, the application automatically creates a Python virtual environment and installs pipeline dependencies.

The graphical user interface (GUI) provides:
\begin{itemize}[itemsep=1pt]
    \item \textbf{Onboarding wizard:} API key validation, output directory selection, research-use disclaimer.
    \item \textbf{Query builder:} PubMed search with relevance scoring and paper selection.
    \item \textbf{Live pipeline monitor:} Real-time progress, per-stage breakdown, Gemini API usage tracking, and technical logs for debugging failed runs.
    \item \textbf{Results explorer:} Sortable table with confidence badges (CORROBORATED, SUPPORTED, LIMITED EVIDENCE, NEEDS REVIEW; Table~\ref{tab:confidence_badges}), plain-language confidence explanations, evidence/provenance fields, and comma-separated values (CSV) or Excel (XLSX) export.
\end{itemize}

\subsection{Validation Framework}
\label{subsec:validation}

\subsubsection{LLM Output Validation Heuristics}

After candidate discovery, ResearchShop tests each gene in the order below. A row that fails a required test remains in the audit files and is left out of the primary export.

\begin{enumerate}[leftmargin=*,itemsep=3pt]
    \item \textbf{Source grounding.}
    The reported label must occur in the fetched article: the canonical symbol, an accepted alias, or the raw wording returned by the model. This removes a real gene that the model remembers when the paper does not mention it.

    \item \textbf{Gene-symbol check.}
    The reported label is accepted when it matches an approved HGNC symbol, an accepted alias, or a previous symbol, and it is mapped to the current approved symbol. The lookup uses the bundled HGNC snapshot, then the HGNC REST service, then MyGene.info~\cite{braschi2019genenames,hgnc_rest_docs,wu2013biogps}. When the label is absent from those records, MyGene.info may return a similarly spelled gene name, such as BRCA1 for a reported label BRAC1. ResearchShop keeps that name as a suggestion for the reviewer and leaves the row unresolved.

    \item \textbf{Variant check and confidence score.}
    A variant string is compared with HGVS-oriented protein, coding, genomic, splice, indel, copy-number, translocation, and cytogenetic patterns~\cite{denDunnen2016hgvs}. A pattern match supports the row. A string that does not match stays visible as review metadata. The confidence score is calculated at this step,
    \begin{equation}
    C_{\mathrm{total}} = C_g + C_v
    \label{eq:confidence}
    \end{equation}
    where $C_g = 0.7$ for a validated gene ($1.0$ for gene-only rows) and $C_v = 0.3$ for a syntactically valid variant.

    \item \textbf{Field and quotation extraction.}
    For each gene that remains, the model fills the user-defined columns and returns a quotation for each filled field.

    \item \textbf{Quotation check.}
    Each quotation is tested in three steps.
    \begin{enumerate}[leftmargin=*,itemsep=1pt]
        \item \textbf{Find the quotation.}
        Fewer than five words must match the article word for word. A longer quotation may differ in spacing or line breaks when the similarity score is at least 0.85~\cite{python_difflib,ratcliff1988gestalt}.

        \item \textbf{Keep the numbers.}
        Every number in the quotation, including p-values, odds ratios, percentages, cohort sizes, and positions, must appear within about 500 characters of that match.

        \item \textbf{Keep the gene beside the quotation.}
        The gene symbol or an accepted alias must appear within about 1,500 characters before or after the match. A mention elsewhere in the article is not enough.
    \end{enumerate}
    The 0.85 score and the two windows are program settings, not biological cut-offs.

    \item \textbf{Export cutoff.}
    The primary table receives a row only when the score from step 3 is at least 0.7 and the quotation checks that apply to that row have passed. The 0.7 cutoff is a workflow setting, not a probability of biological correctness.
\end{enumerate}
